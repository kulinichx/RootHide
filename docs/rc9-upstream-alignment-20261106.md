## iOS 16 适配硬门槛

RC9 的适配目标是 **RC9 3.0.7 越狱路径实际支持的全部 iOS 16.x 系统版本与设备组合**，不是只针对 iPadOS 16.5 或单一测试设备。上游代码不会因为已发布就直接照搬：

- 不提高 RC9 的最低系统版本；App Debug/Release 与最终 TIPA 均保持 `16.0`。
- 维护并逐项核对 RC9 可越狱的 iOS 16.x 版本、设备/芯片、漏洞与偏移组合；不得把 `MinimumOSVersion = 16.0` 当成整张越狱兼容矩阵已经通过验证。
- “全部 iOS 16 越狱版本”指 RC9 这条 3.0.7 RootHide 实现实际支持的版本/设备组合，不表示每个设备都能越狱每个 iOS 16.x 小版本；未盘点或未验证的组合必须明确标注。
- 只移植在 iOS 16 上可用、语义正确的修复；依赖 iOS 17 或更高版本的行为排除。
- 若较新 API 只是可选路径，必须有 iOS 16 可用的 fallback，并明确做 availability 检查。
- 每次比较都核验 API/ABI、系统结构和私有接口在 iOS 16 的实际条件。
- CI 通过不等于设备验收；在用户 iOS 16 设备上的验证单独记录。

当前完整版本/设备兼容矩阵仍待逐项盘点；构建成功和包内最低系统版本校验不替代该项工作。

### fork 握手

补充参考：ZQBB `c15b99798c64ee0c9004b5a7473d0adae0fe995c`。
官方固定参考仍是全局管道、不检查握手结果的实现；本项属于 ZQBB 补充修复，
不标成官方已有同一补丁。

- 每次调用拥有独立、初始化为 -1 的管道状态，不再相互覆盖全局描述符数组。
- 管道建立中途失败会释放已创建端点，向调用者返回错误，不直接 abort 父进程。
- 两个写端设置 Darwin `F_SETNOSIGPIPE`；父子分支先关闭各自不用的端点。
- 原始 read/write 包装将系统调用 carry 错误转换为负 errno；
  EINTR 重试，EOF 和其他失败不再当成握手完成。
- 只有子进程就绪且现有 Mach 权限修复成功，父进程才发送放行字节。
  失败时父进程终止并回收子进程，保存原始错误；
  子进程握手失败用原始 exit 退出，不运行未经修复的调用方代码。
- 保持现有 systemhook hook 安装和 Mach 消息协议，不引入新注入策略。

这不证明所有并发 fork 的继承端点生命周期或 fork 后配置锁已经解决；
后者仍为独立待审项，也没有把补丁认定为用户设备重启或 PPL 等待的根因修复。

## 第六阶段：注入配置快照与 fork 子进程

对照 ZQBB `aa61a300bcbd8ab87bac4296b48e41ccd2808708` 的配置快照提交，
复核 RC9 的 `BaseBin/shared/RCInjectPolicyCache` 与所有调用点。

### 发现与处理

- RC9 原有每份配置独立的 `os_unfair_lock` 缓存能保护普通线程并发，
  但锁内状态直接嵌在调用方静态对象中。多线程进程在另一个线程持锁时
  fork，子进程会继承已锁住的状态；原持锁线程不会出现在子进程。
- 缓存原先按设备、inode、大小、mtime 判断是否刷新，没有纳入 ctime；
  同一文件原地改写并恢复 mtime 时可能继续使用旧配置。
- 原先 mmap 后直接解析，读期间文件被截断/改写存在不稳定窗口。

已改为每个缓存按 PID 发布独立状态。子进程通过 lock-free 原子指针换成
新的未锁状态，不触碰可能继承的锁与 XPC 对象；旧状态留给进程退出回收。
这与 ZQBB 的 fork 隔离目标一致，但保留 RC9 原有按调用点划分的缓存结构，
没有照搬 ZQBB 的全局有界 LRU。

配置改为从同一个文件描述符读入完整缓冲区，再比较读取前后的设备、
inode、类型、大小、mtime 与 ctime 后解析；短读、错误和读取期间修改
不会发布新快照。无效/临时不可读的内容保留上次有效快照；路径确认删除
或变为非普通文件时清除缓存。注入名单文件存在与否、黑白名单规则、
配置键与调用顺序均未更改。

与上游语义的一个明确变化是：RC9 原先遇到稳定的空/损坏配置会清除旧快照，
现在改为保留上次有效值，避免管理器更新窗口让策略短暂退化；如果损坏文件

## 第七阶段：信任缓存与更新中断恢复核查

日期：2026-11-07。检查基线为 RC9 `5f156478`、官方 RootHide `9617d75f`
和 ZQBB RootHide `7e14aa61`。本阶段是代码路径与测试边界核查，没有修改运行时代码。

### Trustcache 内核读者生命周期

- `jb_trustcache_add_entries` 与 `jb_trustcache_clear` 使用
  `gJbTrustcacheLock` 串行化 RC9 自有缓存的追加/清空。
- `trustcache_file_upload` 更新 UUID trustcache 时不持有该锁；
  `is_cdhash_trustcached` 等遍历也不持有该锁。因此该锁不构成内核读者的
  quiescence 或回收屏障。
- 同尺寸替换直接改写已发布 trustcache 的内容；尺寸变化则摘链后等待
  10 毫秒再释放旧分配。代码注释本身也将等待描述为对在途读取的希望，
  不是可证明的生命周期协议。
- 该更新方式在固定官方与 ZQBB 参考中也存在。它是共享的高风险设计边界，
  不是已证实的 RC9 单独回归；不能靠给用户态 mutex 扩大保护范围或任意延长
  sleep 就宣称修复。需要先证明内核读者同步/分配回收语义，才能安全设计变更。

### Generated dyld

- RC9 将生成结果先写入 `gen/dyld.inflight`；普通 move 返回失败时会尝试把
  `gen/dyld.old` 移回 `gen/dyld`。这比固定上游中不检查 move 结果更完整，
  但只覆盖函数仍在运行并收到失败返回的场景。
- 若进程在旧 `dyld` 已移到 `dyld.old`、新文件尚未移到 `dyld` 的窗口内终止，
  当前代码没有启动时 journal/recovery 路径直接从 `dyld.old` 恢复它。安装清理逻辑
  会在需要时隔离损坏的 `dyld.old`，不是 live dyld 恢复器。
- 另有一个较晚、依赖用户操作的兜底：下一次用户手动重新越狱时，
  `prepareBootstrapWithCompletion` 会在 `loadBasebinTrustcache` 前调用
  `replaceBasebinFromBundledArchive`，重新发布 App 内置整份 basebin，然后后续流程
  再生成 patched dyld。它能丢弃旧的半成品状态，但不是 launchd 更新事务的回滚/journal，
  也可能把设备上的 live 更新退回到当前 App 内置版本。
- 现有 `tests/test_rc9_dyld.py` 覆盖同步 remove/move 故障和即时回滚，
  不模拟每个文件操作完成后突然终止并重新启动的恢复过程。

### Live basebin 更新

- `jbupdate_basebin` 先将归档解到临时目录、检查版本和 daemon plist，并在替换前
  准备 trustcache；随后逐个删除 live `/basebin/<item>` 再复制新项目。
- `JBUPDATE_PREV_VERSION` 与 `JBUPDATE_NEW_VERSION` 是进程环境标记；
  正常返回失败时 `@finally` 会清理标记和临时解包目录，但没有每项目备份或
  持久事务 journal。因此在多个 live 项目已替换后发生失败/进程终止，
  现有代码不能证明整批更新会回滚。
- `DOBootstrapper` 的 stage/ready/backup 保护的是应用引导时的整目录发布，
  并非 `jbupdate_basebin` 的 live 更新事务，不能计作自动 journal/回滚覆盖；
  但下一次显式越狱时重新发布 App 内置 basebin，可作为人工触发的整包重建兜底。
- 现有 `tests/test_rc9_update.py` 注入 remove/copy 的同步失败，但不验证前序
  已替换项目的回滚，也不模拟进程在替换序列中途终止。

### 阶段结论与关闭条件

RC9 对更新前校验和同步错误处理已有加固；固定官方/ZQBB 参考没有可直接移植的
持久中断恢复协议。live 更新在当前会话中没有持久回滚；后续手动重新越狱时存在
从 App 内置归档整包重建的兜底，但有回退版本的代价。上述窗口仍暂列未关闭的
更新路径风险，不把它们当作已证实的设备重启根因，也不以真机 CI 或源码测试替代恢复证明。

若要求中断后自动继续或回滚，而不是等待用户手动重新越狱并接受归档版本重建，
必须先定义可持久化、幂等的恢复状态；对每个 rename/remove/copy 阶段做终止注入，
验证恢复在 launchd 更新 finalizer 消费不完整状态前发生，同时保留旧 vnode、
`.fakelib` 挂载和 RootHide 路径语义。
